# No host round trips: +36-45% (T7.2)

*2026-10-23*

**Did:** Profiled T7.1 first: the GPU was busy only 61% of the time. Per layer it waited for three small downloads
(input and expert ids for the CPU), a host synchronize, four small uploads and the CPU result upload. Three of the
uploads were the experts' scale tensors, which `--n-cpu-moe` also keeps in RAM; pinning only the expert weights
(`-ot ...exps\.weight=CPU`) removed them (+4-8% by itself).

Then removed the rest with two new ggml ops (patch `0002`):
- *send* (a GPU kernel) writes the layer input, expert ids and router weights into pinned host memory and raises a
  counter; it also hands the expert matmuls their cache slots;
- a host thread sees the counter, computes the misses on the CPU pool and writes the sum back;
- *recv* (a GPU kernel) waits for the answer and adds it.
The GPU never waits for the host to read something, and a whole token now runs as one CUDA graph. The same path
handles batches of 1-32 tokens, which fixes T7.1's slow short prompts.

**Expected:** ~2 ms per token of host round trips removed, toward ~135-145 tok/s.

**Got:**

| Same chat prompts, 32K context | Gen tok/s: short / 2K / 8K | Prompt tok/s: 19 tokens / 8K |
|---|---|---|
| llama.cpp cache (baseline) | 86.1 / - / 82.5-82.9 | 72-127 / 1,059 |
| T7.1 | 110 / 100.5 / 96.5 | 26 / 1,046 |
| **T7.2** | **124.5 / 117 / 112.5** | **127-139 / 1,075** |

- +36-45% generation over llama.cpp's cache; GPU busy 90% (was 61%); quality unchanged (KL 0.00294 vs all-GPU).
- A crash on the way: misses shared one zero slot, so a token with two misses read the same expert twice, which
  CUDA's MMQ kernel (batches > 8 tokens) does not allow. Fixed with one zero slot per rank (6 slots, ~10 MB).

**Takeaway:** Close to the 135-145 tok/s target. The GPU is now the limit; next is the adaptive cache (T7.3), then
small GPU-side savings (skip the zero-slot matmuls).
