# Ready for daily use: launcher, agent configs, soak test

*2026-10-23*

**Did:** Wrote `run-flint.sh` (all the tuned flags; expert cache sized from the context; P-core threads found from
`/sys`; n-gram speculation; Flint's recommended sampling), OpenCode and pi configs in `clients/` set to a 64K
context, and committed the routing profile that seeds the cache (`profiles/flint-coding.txt`). Then a 30-minute soak
test (`bench/soak.sh`: agent episodes of 4 x 12 turns, back to back) and a 10-minute test with 2 parallel requests.

**Expected:** No leaks, no slowdown, no hangs from the GPU waiting on the CPU.

**Got:**
- 30 minutes: 24 of 25 rounds done; ~74 s per round with no drift; generation 112-119 tok/s at the start and at the
  end; server memory flat at 29-31 GB after warm-up, VRAM flat at 14.8-15.1 GB; no engine errors or timeouts.
- One round stopped: Flint wrote `printf 'QQQQTEST` and hundreds of `Q`s until the 256-token limit, the tool-call
  JSON was cut off, and llama-server answered HTTP 500. This looks like a greedy-decoding repetition loop (the
  benchmark runs at temperature 0; 1 turn in ~1,200), not an engine fault, but I cannot prove stock llama.cpp would
  never do the same on that turn. Real use runs at temperature 1.0.
- 2 parallel requests: stable, no errors, cache hit rate 85.6%; total throughput only ~15% higher, because
  generation is GPU-bound.
- My soak script hung after the test (its final `wait` included the server); fixed.

**Takeaway:** The engine is stable enough to use every day: `./run-flint.sh`, then OpenCode with
`clients/opencode.json`. One request at a time is the right default.
